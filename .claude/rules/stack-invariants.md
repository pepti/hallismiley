# Stack invariants (Orange Smiley engine — auto-loaded rule)

These are contractual. Violations get rejected in review (`invariant-reviewer` agent enforces them). The canonical copy lives in the engine repo (`orangesmiley`, tracked at `.claude/rules/stack-invariants.md`) and reaches every downstream by `git merge upstream/master` (D-021, 2026-09-22).

1. **Vanilla JS SPA.** No React/Vue/Svelte, no bundler, no build-step-only syntax. ES modules + plain DOM.
2. **CommonJS server** (`"type": "commonjs"`). No piecemeal ESM conversion.
3. **One auth system:** Lucia v3 owns sessions. Never bolt on a second mechanism. (The long-claimed "RS256 JWT for stateless API auth" never existed — boilerplate disproved in icelandicstore 2026-08-20 and verified here 2026-08-22: zero jwt code; the .pem files in keys/ are vestigial.)
4. **Migrations — two arrays, one runner.** The authoritative list is `[...engine, ...product]`, assembled by `server/config/migrationSet.js` and applied by `server/scripts/migrate.js` (`npm run migrate`, also at boot; one transaction per entry under an advisory lock; identity is the `name` string). The **engine** array in `server/config/schema.js` is authored only in the upstream repo (orangesmiley) and arrives in a downstream by `git merge upstream/master`; names are `NNN_snake`. The **product** array in `server/config/product-migrations/<product>.js` (product id from `engine.json`) is owned by this repo; new names are `<product>_NNN_snake`, numbered per product; entries in its `legacy` section keep their pre-split unprefixed names and are frozen. Numbers are per array — the prefix is the namespace. A product migration may depend on engine tables; an engine migration never depends on product tables, and never updates product-editable content (site copy, seeds) — those are product migrations. `aliases`/`superseded` in the product file tell the runner which engine names this product's databases already satisfy under another name, or must never execute; they are reviewed like migrations, and `node server/scripts/migrate.js --plan` shows what a run would do without executing. Never edit or rename an applied entry (either array) — append (`/migration-new`, which picks the array). A matching `.sql` under `server/migrations/` is a reference copy the runner does not read.
5. **Error envelope:** all routes return the documented error shape; typed errors → central middleware. No ad-hoc shapes.
6. **Logging:** pino only. No `console.log` in committed code outside one-off scripts.
7. **Security posture:** helmet/CSP, csrf-csrf on state-changing routes, hpp, express-rate-limit, sanitize-html, RBAC role checks, Stripe webhook-signature verification, Sentry error capture. Tighten, never loosen; exemptions need an inline comment + reason.
8. **Server-side gating first:** auth/approval checks live in middleware on the routes; SPA route guards are a UX layer, not the security layer.
9. **Tests hit real Postgres** — never mock `pg`. E2E via Playwright.
10. **i18n:** EN + IS locale JSON in sync; `npm run check:i18n` before pushing translation-touching changes.
11. **Secrets:** `.env`, `keys/`, `data/import/` are gitignored — never committed, never copied between customers.
12. **Customer source platforms are READ-ONLY.** Imports come from exports in `data/import/`; nothing ever writes back to the customer's live platform.
13. **Theme system:** the base ships a multi-theme engine — `public/css/themes.css` (token sets per `html[data-theme]`), a render-blocking `public/js/theme-boot.js` in `<head>`, plus `services/themePrefs.js` + `ThemeSwitcher`. `classic` owns the `:root` token set (= no `data-theme` attribute); the theme a visitor gets with nothing stored is `DEFAULT_THEME` in `themePrefs.js` and `theme-boot.js` (`ember`/Glóð since 2026-09-02) — keep the two files in sync and never conflate the two ideas again. Re-skin by re-hueing token *values* (keep the machinery); never delete the boot script or hardcode one palette over `data-theme`.
14. **A release's migrations must be backward-compatible with the previous release's code** (expand/contract). Self-update means an instance can pull a new image at 03:00 with nobody watching, and during the swap the OLD container is still serving requests against the NEW schema — a `DROP COLUMN` in the same release that stops writing to it takes the site down for the length of the swap, and makes a rollback to the previous digest impossible. So: expand (add the column/table, write both, read new-with-fallback) in release N, contract (drop the old) in release N+1 or later. A release that cannot satisfy this declares `minCompatibleVersion` in its manifest, which the update checker records and refuses to auto-apply from an older instance. Never run an apply during boot migrations — post-boot verification is what closes the loop (`server/services/updateApplier.js`, `docs/SELF-UPDATE.md`). Applies to both migration arrays.
15. **Every new UI feature must survive a theme switch.** Three token sets ride html[data-theme] (Bjart · Glóð · Miðnætti since 2026-09-02); a colour that only works on one of them is a bug. Concretely: no colour literals in component CSS for anything that reads (use the tokens, incl. the status set --success/--warning/--error/--danger + -dim washes); canvas surfaces (Chart.js) read utils/chartTheme.js at draw time — a canvas does not react to the data-theme flip; measure composited contrast on the themes whose surfaces differ (the light trio vs the dark pair). Method: icelandicstore docs/theme-audit-2026-08-21.md.
